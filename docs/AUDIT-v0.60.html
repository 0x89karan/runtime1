The headline theme why this pass mattered

The trust story is partly claimed-but-not-built

For a product whose thesis is “observability & governance is half the value,” the transport hardening is real — but several advertised audit and isolation guarantees don’t hold in code: a receipt-signing key a tool can read, an content_audited:true that audits nothing, a secret-rewriter that was never built, an OTEL “credential guard” that doesn’t exist, and sandbox isolation that fails open. These are exactly the properties AgentOS sells.

Phase 10 — cred.3 credential gateway deep-dive, folded in

The whole-system pass excluded cred.3 internals (covered by a prior 4-voice review). Those findings are folded in here. ar-01…05 are already filed in TODOS; ar-06…10 are added by this update. Reassuring: the gateway is not the open relay first feared — redirects disabled, timeouts + body caps + loopback bind + per-token provider denial are all present, and upstream_base is config-only (not caller-reachable).
cred.3-ar-04P2filed
SSRF — no IP-level block on upstream_base

Validated https:// only; no DNS-resolve + private/loopback/link-local block. A template/misconfig pointing at IMDS (169.254.169.254) gets live bearer tokens attached. The Python tools it replaced had this guard.

credential/mod.rs:665 — mirror oauth_mcp `_is_ssrf_blocked()`
cred.3-ar-06P2new
state_path is written but never read back

The writable token cache (the point of the two-tier storage) is write-only: startup always re-reads the original /run/secrets token. With Google's single-use rotation, re-auth silently breaks after any restart (worst on QEMU/OS-boot).

credential/mod.rs:184,235 — read state_path on init, prefer rotated token
cred.3-ar-07P2new
Gateway token scoped per-MCP-server, and missing caps → all providers (fail-open)

The registry stores server.name as the agent_id (audit-attribution confusion), and an MCP server with no capabilities block is granted every configured provider.

main.rs:530,544 — deny-by-default; scope to owning agent
cred.3-ar-08P2new
Inbound header scrubbing is a blocklist (fail-open)

Unlike the model-key proxy's whitelist, the gateway forwards all inbound headers except a scrub list → a compromised tool can smuggle extra headers to the provider alongside the injected credential.

credential/mod.rs:355 — switch to a whitelist
cred.3-ar-09P2new
Mesh refresh collision — blocks multi-instance

In-process broker + Google single-use refresh rotation → two instances sharing one credential mutually invalidate each other's token. A shared credential service is a mesh.3 prerequisite; name it before orch.1.
