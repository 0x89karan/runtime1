AgentOS · Docker

Running the Chain of Scouts

Three-agent Gmail orchestrator: cron trigger → inbox reader → KB curator → daily brief.

v0.95.0 — What's new
  • Sealed-job pipeline — the orchestrator is de-privileged new — the node that reads the schedule now holds only {cron_trigger, RunJob}: no Gmail, no KB, no file write, no spawn. It fires two config-declared sealed jobs (cos-inbox reads Gmail; cos-curator writes the brief) whose capabilities and instructions are owned by config, not chosen by the trigger — and it receives only a "job completed" signal, never a job's output. This closes audit P1-10 (an injected trigger cannot reach live Gmail). It does NOT stop an injected curator from writing a misleading brief — that's a social-engineering channel, not a credential path (see THREAT_MODEL §9.5). No setup changes: same OAuth flow, same docker compose up cos. What changed is what you see in the flight log — run_job calls and cos-inbox-…/cos-curator-… job children instead of spawn_agent.
  • Docker :full / :latest publish fixed fixed — the release job had been failing to publish the full image since v0.92.0 (a retired GitHub Actions cache backend returned not_found on cache export, which buildx treated as fatal after the image already pushed). Fixed by making cache export non-fatal. v0.95.0 is the first full image published since; if docker pull …:full gave you a stale build recently, this is why.
  • Brief writes actually work now fixed — earlier v0.86.x images silently denied every write_file call from the CoS orchestrator ("File write" showed as a "known environment constraint" in the daily brief). Root cause: the FsWrite capability grant and the prompt's write path drifted out of sync during Docker's config rewrite. Fixed at the config level; no setup changes needed. If you still see briefs delivered inline instead of written to disk, re-pull the image (≥ v0.86.2).
  • Gmail actually works now — earlier v0.86.x images rejected every Gmail API call with credential_denied/no_providers_configured even after a successful agentctl auth google, because the google_oauth MCP server was missing its own broker capability grant. Fixed at the config level; no setup changes needed. If you still see this error, re-pull the image (≥ v0.86.1).
  • Chat rail on the Dashboard — agentctl watch now has a permanent chat pane beside the agent table. Press Tab to focus it, type a message, Enter to send — replies stream in live, token by token, over the same management API connection you're already using below. See step 07.
  • Credential broker — the google_oauth sidecar no longer holds the raw refresh token in memory. A credential gateway reads google.json once and issues short-lived access tokens per request. No changes to the setup flow below.
  • Management API exposed on :7999 — agentctl watch now runs on your Mac host with --url http://localhost:7999. No more docker exec.
  • Semantic KB requires OpenAI — OPENAI_API_KEY is now a required environment variable for email dedup and semantic search.
Before you start
  • Docker Desktop installed and running on your Mac
  • Anthropic API key (sk-ant-...)
  • OpenAI API key (sk-...) required — for email embeddings
  • Google Cloud account — free tier works
  • Rust + Cargo — to build agentctl once
One-time setup
01
Build agentctl once

You need agentctl on your Mac to complete the Google OAuth flow and to watch the agents from your terminal. Build it from the repo root:

bash
# From repo root
cargo build --release --bin agentctl

# Optionally add to PATH
sudo cp target/release/agentctl /usr/local/bin/agentctl
02
Create Google OAuth credentials once

The CoS needs read-only Gmail access. Create an OAuth app in Google Cloud:

  1. Go to console.cloud.google.com → select or create a project
  2. APIs & Services → Library → search Gmail API → Enable
  3. APIs & Services → Credentials → Create Credentials → OAuth client ID
  4. Application type: Desktop app — name it anything
  5. Copy the Client ID and Client Secret — no redirect URI to register

Desktop app clients allow 127.0.0.1 loopback redirects automatically per RFC 8252 — there is no redirect URI field in the Google Cloud Console for this client type. agentctl auth google uses port 8585 by default; pass --port <N> if that port is in use.

⚠️ Publish to Production before authorizing. On the OAuth consent screen, change Publishing status to Published. Testing-mode refresh tokens expire after 7 days. For gmail.readonly (a non-sensitive scope), unverified Production apps work fine — Google shows a warning screen but tokens stay valid indefinitely.

03
Authorize Gmail access once

Run the PKCE OAuth flow on your Mac. A browser window will open — sign in with your Google account and grant Gmail read access. The refresh token is saved locally and picked up by the credential broker at runtime.

bash
agentctl auth google \
  --client-id     "YOUR_CLIENT_ID.apps.googleusercontent.com" \
  --client-secret "YOUR_CLIENT_SECRET"

On success, credentials are written to ~/.agentos-secrets/google.json. The container mounts this file read-only — the credential broker reads it once at startup and issues short-lived access tokens from there. The raw refresh token never lives in the agent process.

04
Create the output directory once

Runtime state (checkpoint, memory DB, flight log, evidence log) lives in a Docker named volume (cos-data, mounted at /data in the container) that Compose creates automatically — you don't manage it on the host. The one host directory you create is where the daily brief is written; secrets land in ~/.agentos-secrets when you run agentctl auth google.

bash
mkdir -p ~/.agentos-output
Run it
05
Pull the image
bash
docker pull ghcr.io/0x89karan/runtime1:full
06
Start the CoS updated

Set your API keys and run via docker compose, not a bare docker run — since h8.1/memory-routing, cos.agents.toml's semantic KB needs the semantic-kb-mcp sidecar (backed by Qdrant), and that hostname only resolves on the Compose network. A standalone docker run now fails immediately with a DNS error (failed to lookup address information for semantic-kb-mcp). docker compose up cos brings up qdrant + semantic-kb-mcp automatically as dependencies. TRIGGER_INTERVAL=every 2m fires the cron quickly for testing — change it to a cron expression like 0 8 * * * for production use. The management API is bound to 127.0.0.1:7999 so agentctl watch can connect from your Mac terminal directly.

bash
export ANTHROPIC_API_KEY=sk-ant-...
export OPENAI_API_KEY=sk-...
# Use the published image instead of building from source:
export AGENTOS_IMAGE=ghcr.io/0x89karan/runtime1:full

docker compose up cos

The container starts the credential gateway, connects MCP servers (including the semantic KB sidecar), and parks the orchestrator in a cron wait loop. Logs stream to your terminal.

Run from source instead (no published image)? Omit AGENTOS_IMAGE — Compose falls back to building the runtime-full target locally (make dev-image does the same thing, tagged agentos:dev, which is the default when AGENTOS_IMAGE is unset).

What happens in the first 3 minutes
0:00
agentd starts. Credential broker reads google.json. MCP servers connect. The trigger parks in its cron loop — it holds only {cron_trigger, RunJob} (no Gmail, no KB, no file write) and reads nothing the jobs produce (cap.2b).
~0:30
Cron fires. The trigger calls run_job("cos-inbox") — a config-declared sealed job (fixed caps + task, owned by config, not the trigger). A child cos-inbox-YYYY-MM-DD is materialized with a 1.5M budget.
~1:00
Inbox job reads Gmail. Credential broker issues a short-lived access token → Gmail API fetches last 24 h → the inbox job writes the structured OperatingBrief to the KB (ops:entities) itself. The trigger receives only a "job cos-inbox-… completed" signal — never the email content.
~1:30
Curator job runs. The trigger calls run_job("cos-curator") — a KB-only job (no Gmail). It reads the inbox result from the KB, persists briefs + entities (redb + Qdrant embeddings via OpenAI).
~2:00
Brief written. The curator job (which owns FsWrite + brief publishing) writes brief-YYYY-MM-DD.md and publishes it. The trigger gets a completion signal and parks for the next cron.
07
Watch the agents updated

Open a second terminal on your Mac — no docker exec needed. The management API is forwarded to localhost:7999:

bash
agentctl watch --url http://localhost:7999

Use the [c] key for credentials, [a] for approvals, [i] for the flight log inspector. Press q to exit the cockpit — the agents keep running.

Chat with an agent directly new — the Dashboard now has a chat rail beside the agent table. Press Tab to focus it (the border turns white), select an agent row and press r to retarget the rail to it, type a message, then Enter to send. The reply streams in live, token by token, in green. Esc or Tab again returns focus to the table; ↑/↓ scroll the transcript while focused, End jumps back to the live tail.

Note
Chat needs the management API connection (--url, exactly what step 07 uses) — it streams replies over the same SSE connection as the rest of the cockpit. If you run agentctl watch --agents-dir /agents against the FUSE mount instead (no --url), the chat rail will accept a typed message but never show a reply — retarget with Tab/r or use --url as shown above.
08
Read the brief

Once the first cycle completes, the brief lands on your host:

bash
# List briefs
ls -la ~/.agentos-output/

# Read today's brief
cat ~/.agentos-output/brief-$(date +%Y-%m-%d).md
Updating & older images
Stopping the CoS
  • Ctrl+C in the terminal running docker compose up cos stops the cos container with a graceful checkpoint. qdrant and semantic-kb-mcp keep running in the background (cheap to leave up between sessions).
  • Stop everything (cos + qdrant + semantic-kb-mcp): docker compose down — removes the containers + network, but keeps named volumes (your data).
  • Not sure what's running? docker ps -a --filter name=agentos lists every AgentOS container; remove leftovers with docker rm -f <name>.
  • Your data is safe. Runtime state lives in the cos-data named volume (/data in the container) and briefs on the host at ~/.agentos-output — removing a container never touches either. The only destructive command is docker compose down -v, which also deletes named volumes (cos-data plus Qdrant's index — re-embeds from scratch on next run).
After every release — re-pull
  • The image is the code. Fixes ship as new agentos:full builds; a running container never updates itself. A stale local image is the #1 cause of "a fix landed but nothing changed."
bash
# 1. Pull the newest build
docker pull ghcr.io/0x89karan/runtime1:full

# 2. Remove the old container
docker rm -f agentos-cos 2>/dev/null || true

# 3. Re-run step 6 with the fresh image
Clean re-test after a fix (drop stale / failed agents)
  • A restart resumes prior agents from the checkpoint — by design. But that includes any agent that failed in an earlier run. After pulling a fix, start fresh rather than reloading broken state.
bash
# 1. Stop the containers AND drop the cos-data volume so no stale
#    (or failed) agents reload from the checkpoint. -v also clears
#    Qdrant's index (re-embeds on next run).
docker compose down -v

# 2. Pull the fixed image
docker pull ghcr.io/0x89karan/runtime1:full

# 3. Re-run step 6

Why -v: the checkpoint, memory store, flight log, and signing keys all live in the cos-data named volume — there is no ~/.agentos-data on the host to rm. docker compose down -v is the clean-slate reset. Google credentials in ~/.agentos-secrets (a separate host mount) are not touched.

Troubleshooting
  • Inbox agent stuck at "Not authenticated" / "no active session": your image predates the credential broker. Re-pull agentos:full (≥ v0.83.0) and restart.
  • Gmail calls return 403 credential_denied / no_providers_configured, even though agentctl auth google succeeded and oauth_check_auth reports "ready": your image predates v0.86.1 — the google_oauth MCP server was missing its own broker capability grant (agent-level Credential alone isn't enough; the server needs one too). Re-pull agentos:full (≥ v0.86.1) and restart. If building from source, make sure your checkout includes commit f5b3555f or later.
  • Daily brief says "File write: FsWrite capability denied" / brief only shows up inline in the orchestrator's reply, never on disk at ~/.agentos-output: your image predates v0.86.2 — the Docker config rewrite updated the FsWrite grant to an absolute path but not the matching write_file prompt instruction, so every write was silently denied. Re-pull agentos:full (≥ v0.86.2) and restart.
  • agentd exited with error: connecting to HTTP MCP server 'semantic-kb': ... dns error: failed to lookup address information: you started cos with a bare docker run instead of docker compose up cos. semantic-kb-mcp is a separate sidecar container (h8.1/memory-routing) reachable only by its Compose service name — there is no standalone-docker run path for cos mode anymore. Use step 06's docker compose up cos command.
  • Container exits with "ANTHROPIC_API_KEY is not set": the key wasn't in the shell that ran docker compose up. Re-export it, or put ANTHROPIC_API_KEY=sk-ant-... in ~/.agentos-secrets/agentos.env (the entrypoint sources it).
  • Semantic KB not working / "OPENAI_API_KEY is not set": make sure OPENAI_API_KEY is exported in the same shell before docker compose up cos — it's forwarded by the cos and semantic-kb-mcp services' environment: blocks.
  • agentctl watch can't connect: confirm the container is running with -p 127.0.0.1:7999:7999 — older invocations without this flag won't expose the port. Verify with curl -s http://localhost:7999/healthz.
  • Chat rail sends a message but the reply never appears: you're likely connected via --agents-dir /agents (FUSE) instead of --url http://localhost:7999 — the chat rail needs the management API's streaming connection, which FUSE mode doesn't provide. After ~30s you'll see an inline "No response after 30s" hint; reconnect with --url as shown in step 07.
  • Browser shows ERR_CONNECTION_REFUSED during auth: port 8585 was already in use. Re-run with --port <free-port> — Desktop app clients accept any loopback port automatically.
  • No brief after a few minutes: check the cron fired — docker compose exec cos jq 'select(.kind=="mcp_tool_called")' /data/flight.jsonl | tail.
  • Logs & receipts: the flight log and evidence chain live in the container at /data (the cos-data volume). Inspect with docker compose exec cos jq . /data/flight.jsonl; verify the signed action-receipt chain with docker compose exec cos agentctl verify /data/evidence.jsonl.
Notes
  • Schedule: TRIGGER_INTERVAL="every 2m" (used above) only accepts every N(s|m|h). For a daily brief use -e "TRIGGER_CRON=0 8 * * *" (08:00 UTC). A cron expression in TRIGGER_INTERVAL will not parse.
  • API key across shells: Compose's bare - ANTHROPIC_API_KEY (no =value) forwards it from the shell you exported in — run docker compose up cos in that same terminal.
  • Talk to it interactively: instead of the autonomous cron brief, run the orchestrator REPL — docker run --rm -it -e ANTHROPIC_API_KEY ghcr.io/0x89karan/runtime1:full orchestrate.
  • Stopping: Ctrl+C triggers a graceful checkpoint. State is preserved in the cos-data volume (/data in the container) — the next run resumes from where it left off.
  • Google auth on subsequent runs: The refresh token in google.json is read by the credential broker; no browser re-auth needed. If the token expires, re-run agentctl auth google with the same flags.
  • Privacy — email embeddings: The CoS sends email body content (up to 8 KB per message) to OpenAI's Embeddings API for vectorisation. Review OpenAI's data usage policies before enabling on inboxes with sensitive content. To run without OpenAI (BM25 only), omit OPENAI_API_KEY and remove the semantic-kb block from cos.agents.toml.
