## Goal

Make the `watcher` template (currently gated/non-functional) fully operational
by shipping three event-trigger MCP servers that expose a single blocking tool:
`wait_for_trigger()`. The agent calls it as its first action each turn; the
server blocks until the condition fires (cron schedule, filesystem change, or
HTTP webhook). No scheduler, Rust, or core-runtime changes.

---

## Roadmap spec (verbatim)

> Trigger sources (cron expression, filesystem watch, HTTP webhook) are MCP
> servers that expose a single blocking tool: `wait_for_trigger()`. The agent
> calls it as its first action; the server does not return until the condition
> fires. `agentd`'s existing "agent waiting for a tool result" mechanism handles
> the rest — no scheduler changes needed. The agent wakes from a checkpoint,
> runs its loop to completion, and is re-checkpointed by the scheduler to sleep
> again. The agent itself is never aware it is being triggered; it wakes as if
> from a fresh prompt.

---

## Critical constraint: MCP_TIMEOUT = 30 s

`agentd/src/tools/mcp.rs:23` defines `const MCP_TIMEOUT: Duration = Duration::from_secs(30)`.
Any tool call that blocks longer than 30 seconds is killed and the MCP client
is marked broken. This is a hard constraint for HARNESS increments (no Rust
changes allowed).

**Consequence:** `wait_for_trigger()` must use a **poll-and-retry** design:
- Tool accepts `timeout_s: int` (default 25, max 25 — safely under MCP_TIMEOUT=30)
- Server blocks for at most `timeout_s` seconds, then returns
- Returns `{"status": "waiting", ...}` if condition not yet met
- Returns `{"status": "fired", ...}` when condition fires
- Agent's task instructs it to loop calling `wait_for_trigger()` until `status == "fired"`

This is safe: the MCP server process is long-running (not restarted per call),
so state (next cron time, FS snapshot, webhook queue) persists between calls.

## Scope

### Three new Python MCP servers (docker/)

1. **`docker/cron_mcp.py`** — fires on a cron schedule or fixed interval
   - Tool: `wait_for_trigger(timeout_s=25)` → `{status, fired_at?, next_fire?}`
   - Config: `TRIGGER_CRON` (5-field expression e.g. `"0 9 * * *"`) OR
     `TRIGGER_INTERVAL` (human interval e.g. `"every 5m"`, `"every 1h"`)
   - Implements minimal 5-field cron parser using stdlib only (no `croniter`)
   - Fires immediately if scheduled time was missed since last fire

2. **`docker/fs_watch_mcp.py`** — fires when watched directory/file changes
   - Tool: `wait_for_trigger(timeout_s=25)` → `{status, changed_files?, snapshot_id?}`
   - Config: `TRIGGER_WATCH_PATH` (required), `TRIGGER_POLL_INTERVAL_S` (default 2)
   - Polling via `os.stat()` mtime + size; no `watchdog` dep
   - Returns list of new/modified/deleted paths relative to watch root
   - Resets snapshot after each fire so next call starts fresh

3. **`docker/webhook_mcp.py`** — fires when HTTP POST arrives on a local port
   - Tool: `wait_for_trigger(timeout_s=25)` → `{status, method?, path?, body?, headers?}`
   - Config: `TRIGGER_WEBHOOK_PORT` (default 9000), `TRIGGER_WEBHOOK_HOST`
     (default 127.0.0.1), `TRIGGER_WEBHOOK_SECRET` (optional HMAC-SHA256)
   - Listener thread started at server startup; requests queued in `queue.Queue`
   - Queue capacity: 10 (drops oldest on overflow — logged to stderr)
   - Body cap: 64 KB (matching shell_mcp.py)
   - HMAC validation: checks `X-Hub-Signature-256` header when secret set

### Template updates

## What is NOT in scope

- `inotify`-based fs watching — polling is cross-platform, zero-dep, sufficient
- External Python deps (`croniter`, `watchdog`, `APScheduler`) — stdlib only
- Multi-trigger fan-out (wait for cron AND webhook) — single trigger per server
- Agent restart after trigger completes — the agent loops via task instruction;
  the scheduler's existing periodic checkpoint handles agentd restarts
- Rust/scheduler changes — HARNESS boundary, no Rust modifications
- Webhook TLS — `http.server` is HTTP-only; TLS can be added via nginx reverse
  proxy at the operator level
- Trigger history / audit log — out of scope; flight recorder captures tool calls

## MCP tool schema (all three servers)

```json
{
  "name": "wait_for_trigger",
  "description": "Block until the configured trigger fires, then return trigger details. Returns {status: 'waiting'} if the condition did not fire within timeout_s seconds — call again to keep waiting. Returns {status: 'fired', ...} when the condition fires.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "timeout_s": {
        "type": "integer",
        "description": "Max seconds to wait before returning 'waiting'. Default 25, max 25."
      }
    },
    "required": []
  }
}
```

### Return value when fired (cron)
```json
{"status": "fired", "trigger_type": "cron", "fired_at": "2026-06-27T09:00:00Z", "expression": "0 9 * * *"}
```

### Return value when fired (fs_watch)
```json
{"status": "fired", "trigger_type": "fs_watch", "fired_at": "2026-06-27T09:00:00Z", "watch_path": "/workspace", "changed": [{"path": "src/main.rs", "change": "modified"}, {"path": "README.md", "change": "new"}]}
```

### Return value when fired (webhook)
```json
{"status": "fired", "trigger_type": "webhook", "fired_at": "2026-06-27T09:00:00Z", "method": "POST", "path": "/", "body": "...", "content_type": "application/json"}
```

### Return value when waiting
```json
{"status": "waiting", "message": "No trigger yet. Next cron: 2026-06-27T09:00:00Z"}
```

## Agent task template (poll loop)

The watcher/cron/webhook templates set the agent task to instruct the poll loop:

```
Watch /workspace for file changes and summarize them.
Your first action each turn: call wait_for_trigger(). If it returns status='waiting', 
call it again immediately. Once status='fired', analyze the changed files and write 
a brief summary to /workspace/change-report.md. Then call wait_for_trigger() again
to wait for the next change.
```

## CEO Phase Outputs

### Premise challenge

**P1 (poll-and-retry is not "agent unaware"):** The roadmap goal states "the agent itself is never aware it is being triggered." The poll pattern contradicts this — the agent must know to call `wait_for_trigger()` in a loop. **Resolution:** Amend goal statement; document that poll is explicit but isolated to the task template. The agent doesn't know WHY it's calling the tool, only that it should. This is an acceptable simplification for HARNESS.

**P2 (separate servers are the right granularity):** Each trigger type has fundamentally different state (clock vs. filesystem snapshot vs. socket listener). Unifying them would create a complex shared-state server with conditional configuration. Separate files are cleaner. **Resolution:** Keep separate.

**P3 (stdlib cron is sufficient):** UTC-only 5-field cron is well-understood and testable. Timezone support adds DST complexity with no clear user demand in the single-tenant AgentOS model. **Resolution:** UTC-only, document limitation.

### Dream state delta

```
CURRENT (h7.2): Agents are reactive only — they can read, write, call APIs,
  but can only be triggered by a human spawn. The watcher template is a stub.

THIS PLAN (h7.3): Three trigger types operational. Agents can wake on schedule,
  on filesystem change, or on HTTP event. watcher/cron-agent/webhook-agent
  templates functional. The OS now has autonomous agents.

12-MONTH IDEAL: Trigger as a first-class scheduler primitive (not an MCP tool).
  Agents declare their trigger source in their config; the scheduler handles
  wakeup, checkpointing, and retry without prompt-level meta-instructions.
  This plan is the stepping stone — it proves the semantics.
```

### NOT in scope (deferred to TODOS.md)

- Unified trigger server (one server, `TRIGGER_TYPE` env var) — valid long-term shape but adds shared state complexity; defer to h8.x or a dedicated p8.x core increment when first-class scheduler triggers are designed
- Timezone support for cron — UTC is correct; TZ support adds DST complexity
- Replay protection for webhooks (requires persistent seen-events store) — timestamp tolerance covers most cases; full replay protection is a future hardening item
- Multi-trigger fan-out (agent waits for cron OR webhook) — requires first-class scheduler support (core change)
- Trigger history/replay — flight recorder captures tool calls; dedicated trigger store is future work

   │                 │ │                  │ │                       │

   │                 │ │  POLL_INTERVAL_S │ │ │ on WEBHOOK_PORT    ││
