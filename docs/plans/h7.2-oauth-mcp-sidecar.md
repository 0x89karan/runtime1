## Roadmap spec

> Handles OAuth2 authorization-code flow with a local callback server; stores tokens in
> the system keychain (read from env at agent startup, preserving the secrets-from-env
> invariant); presents authenticated HTTP calls as MCP tools. Unlocks Gmail, Google Drive,
> Calendar, and other OAuth-gated services. `agentd` sees it as any other MCP server — no
> core changes.

## Scope (revised: generic OAuth sidecar)

A new Python MCP server (`docker/oauth_mcp.py`) that is **provider-agnostic** — configured
entirely by env vars. Google is the first concrete example (via template), not a hardcoded target.

1. **OAuth2 authorization-code flow + PKCE** — starts a local `http.server` callback at
   `localhost:<random_port>/callback`, returns an auth URL for the agent to surface to the
   user via `request_approval`; captures the code, exchanges it for tokens. PKCE
   code_challenge/code_verifier added per RFC 7636 (required for public/installed clients).
2. **Token storage** — refresh token written to `~/.agentos-oauth/<provider>.json` (mode
   0600, created with `O_CREAT|O_WRONLY`, directory created 0700). Env var override:
   `OAUTH_REFRESH_TOKEN` skips the dance entirely.
3. **Three generic tools** (no Google-specific code in the server):
   - `oauth_start_auth()` → starts callback server, returns auth URL
   - `oauth_check_auth()` → returns `{ ready: bool, scopes: [str] }`
   - `oauth_call_api(url, method?, headers?, body?)` → authenticated API call with automatic
     token refresh; host allowlist enforced; 4 MB response cap
4. **Provider configuration via env** (`passenv` in TOML):
   - `OAUTH_CLIENT_ID`, `OAUTH_CLIENT_SECRET` — required
   - `OAUTH_AUTH_URL`, `OAUTH_TOKEN_URL` — required (provider-specific endpoints)
   - `OAUTH_SCOPES` — space-separated scope string
   - `OAUTH_ALLOWED_HOSTS` — comma-separated host allowlist for `oauth_call_api`
   - `OAUTH_REFRESH_TOKEN` — optional, bypasses dance
   - `OAUTH_PROVIDER_NAME` — used as token file basename (default: `oauth`)
5. **Template** — `templates/google-agent.template.toml` with `gated_requires` set;
   sets all `OAUTH_*` env vars for Google accounts.google.com/googleapis.com.
6. **Docs** — `docs/MCP_SERVERS.md` `oauth_mcp` section with Google quickstart.

## What is NOT in scope

- Non-Google provider *templates* — `google-agent.template.toml` is the only bundled example; operators can configure the sidecar for Slack/GitHub/Notion by setting the right env vars
- `agentctl oauth login` subcommand — agent handles the dance via `request_approval` + `oauth_start_auth`
- Encrypted token store (beyond 0600 file permissions) — future hardening
- `keyring` / system keychain integration — env var + file is sufficient for single-tenant
- Write tools (Gmail send, Drive upload, Calendar create) — read/list via `oauth_call_api` first; write is one more `oauth_call_api` call the agent can make with the right URL+method; no additional server code required
- OAuth device-code flow (RFC 8628) — localhost callback + PKCE is the Google-recommended approach for installed apps; device flow requires special GCP project setup

## Acceptance criteria

- `python3 docker/oauth_mcp.py --test` passes without API keys (no-op stub mode)
- `oauth_start_auth` returns an authorization URL containing PKCE `code_challenge` (S256 method)
- `oauth_check_auth` returns `{ready: true, scopes: [...]}` after the dance completes
- `oauth_call_api` makes an authenticated HTTP call; automatically refreshes on 401
- `oauth_call_api` rejects hosts not in `OAUTH_ALLOWED_HOSTS` with `isError: true`
- `oauth_call_api` response body capped at 4 MB
- Refresh token stored in `~/.agentos-oauth/<OAUTH_PROVIDER_NAME>.json` with mode 0600
- Token file directory created with mode 0700 if absent
- `OAUTH_REFRESH_TOKEN` env var bypasses the dance entirely; token file not required
- Token refresh (access token expiry) handled automatically — no agent intervention
- Local callback server binds `127.0.0.1` only, random ephemeral port; shuts down after one code capture
- JSON parse error in MCP framing returns -32700 (inherits h7.1 pattern)
- `passenv` blocklist rejects `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN` (inherits h7.1 guard)
- CI guard: binary under 6 MB (HARNESS, no Rust changes)
- Workspace tests: 1025 existing pass + ≥8 new tests for the Python server
- Startup exits with `oauth_mcp: missing required env OAUTH_CLIENT_ID` when required vars absent
- `templates/google-agent.template.toml` contains `accounts.google.com` and `gmail.googleapis.com` in OAUTH_ALLOWED_HOSTS
- `oauth_call_api` rejection body is `{"error": "host_not_allowed", "host": "<hostname>"}` with `isError: true`
- `docs/MCP_SERVERS.md` oauth_mcp section exists with GCP checklist and approval dance documented

## Security properties

- Client ID/secret always from env via `passenv`, never from file or hardcoded
- Refresh token: env var (preferred, secrets-from-env invariant) or 0600 file written by server itself
- Access tokens: in-memory only, never written to disk
- Host allowlist: configurable via `OAUTH_ALLOWED_HOSTS` env var; checked on every `oauth_call_api` call
- PKCE (S256 method): code_verifier generated with `secrets.token_urlsafe(96)`, code_challenge = base64url(SHA-256(verifier))
- LD_PRELOAD stripping (inherit from h7.1 pattern)
- 4 MB response cap on `oauth_call_api` responses
- Local callback server binds `127.0.0.1:0` (OS-assigned random port), shuts down after first successful code capture
- `McpPassenvForwarded` flight event records which env vars were forwarded (inherits h7.1)
- Known limitation: refresh token on disk at 0600 — operator should prefer `OAUTH_REFRESH_TOKEN` env var for security; file storage is a convenience fallback

## Architecture additions (from eng review)

### Threading model (both voices: critical)

The MCP JSON-RPC loop runs on the main thread (`for line in sys.stdin`). The OAuth callback server
must run on a **daemon thread** (`threading.Thread(daemon=True)`). Token state is shared between
threads and must be protected by `threading.Lock`.

Pattern: callback thread captures only `{code, state, error}` via a `threading.Event`; token
exchange (code → tokens) happens in `oauth_check_auth` on the MCP thread after the event fires.

### `AuthSession` dataclass

```python
@dataclass
class AuthSession:
    state:        str          # CSRF nonce
    code_verifier: str         # PKCE verifier
    redirect_uri: str
    expires_at:   float        # time.monotonic() + 600
    server:       HTTPServer   # callback server
    thread:       Thread       # daemon thread
    result:       dict | None  # {code} once captured; None until then
    lock:         threading.Lock = field(default_factory=threading.Lock)
```

Only one `AuthSession` may be active at a time. A second `oauth_start_auth` while one is pending
cancels the old session (shuts down its server, closes thread) and starts fresh.

### Tool state machine

```
idle → [oauth_start_auth] → pending → [oauth_check_auth success] → authorized
authorized → [token expiry] → expired (auto-refresh on next oauth_call_api)
pending → [10 min timeout] → idle (callback server shut down)
any → [oauth_check_auth with error] → idle
```

`oauth_call_api` in `idle` or `pending` state returns `isError: true` with `{"error": "auth_not_ready"}`.

### Token refresh serialization

`_token_lock: threading.Lock` — acquired before reading/writing in-memory token dict. Token file
written atomically: `tempfile.mkstemp()` → write → `os.chmod(tmp, 0o600)` → `os.replace(tmp, token_path)`.
Double-checked pattern: after acquiring lock, re-read file before deciding to refresh.

### Callback security

- Path must be exactly `/callback`; method must be `GET`
- `state` parameter must exactly match `AuthSession.state` (CSRF per RFC 6749 §10.12)
- Callback server processes only one valid code; second visit returns HTTP 410
- Browser response HTML must not echo back query parameters (no XSS surface)

### SSRF: dual-layer protection for `oauth_call_api`

1. Hostname allowlist: `parsed.hostname in OAUTH_ALLOWED_HOSTS_SET`
2. IP block: `_is_ssrf_blocked(url)` (ported from `http_mcp.py`) rejects loopback/RFC1918/link-local
3. HTTPS-only enforced
4. Redirects not followed

### PKCE verifier length

`secrets.token_urlsafe(64)` → 86-character URL-safe string (RFC 7636 allows 43–128; 128 is the hard ceiling and some servers reject it).

### Test matrix (all mockable, no real Google creds)

1. `oauth_check_auth` before `oauth_start_auth` → `{ready: false, error: "no_session"}`
2. `oauth_call_api` before auth → `isError: true, "auth_not_ready"`
3. `oauth_call_api` with host not in allowlist → `isError: true`
4. `oauth_call_api` with expired token, mock 200 refresh → retries with new token
5. `oauth_call_api` with 400 refresh response → `isError: true`, no crash
6. `oauth_start_auth` twice → second cancels first, new URL returned
7. `OAUTH_REFRESH_TOKEN` set → `oauth_check_auth` returns `{ready: true}` immediately
8. Response body exactly at 4 MB → truncation fires, not error
9. Callback server receives wrong state → returns 400, session stays pending
10. Callback server timeout → server shuts down, `oauth_check_auth` returns `{ready: false, error: "timeout"}`

### `oauth_call_api` timeout

Each sub-request (token refresh + API call) gets a 20s timeout; combined max = ~40s. The MCP
client timeout is 30s (from p7.1). Document this: operators should not rely on 30s exactly for
calls that trigger token refresh. Future: expose `timeout_s` parameter.

## CEO Review Findings

Both voices (Claude subagent + Codex) agree on 5 of 6 dimensions: premises are questionable, scope calibration is off, alternatives were under-examined, PKCE is missing, 6-month risk is high. They agree OAuth integration is the right goal; the implementation approach needs adjustment.

**Cross-cutting concern (both voices):** The plan mixes the generic OAuth dance with Google-specific API tools. The roadmap says "and other OAuth-gated services" — Google-specific hardcoding forecloses that. A generic OAuth sidecar parameterized by provider config + `oauth_call_api` tool is the composable design; Google APIs become a template concern, not a server concern.
