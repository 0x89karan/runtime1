## The defect, as filed in TODOS.md

`HttpSource::load_snapshot()` (`agentctl/src/watch/source.rs:636`) hardcodes
`egress_brokered: 0` / `egress_denied: 0`. The TUI AgentDetail pane renders
`"{} brokered  {} denied"` (`views.rs:1259`), so over `--url` the operator is told zero
denials. TODOS.md states the cause as: *"The FUSE path reads them from live files… Now
FUSE mode shows true counts while HTTP mode still shows a false `0 denied`."* and the fix
as: *"emit the counters from `/api/v1/snapshot` and read them in `HttpSource`."*

# STEP 0A — PREMISE CHALLENGE (the filed premise is FALSE)

Traced the READ path and the WRITE path before accepting the filing. Three of its claims
are wrong, and the third one inverts the whole increment. **Independently confirmed by the
Codex CEO voice**, which reached the same conclusion from the same code and returned
RESHAPE.

### F1 — "The FUSE path reads them from live files." FALSE.

`surfaces/src/agents_fs.rs` exposes `system/egress_addr` and nothing per-agent. Both
transports get these numbers from the SAME client-side source: `count_egress_by_agent()`
(`agentctl/src/watch/reader.rs:364`), which greps `flight.jsonl` line-by-line for the
literal strings `"egress_brokered"` / `"egress_denied"` and buckets by `data.agent`. It is
called from `app.rs:820`, gated on `View::AgentDetail`.

The real split is not FUSE-vs-HTTP. It is **`--log-path` supplied or not** — an explicit
CLI arg (`watch/mod.rs:76`) with no default. A remote `--url` operator has no server-side
flight log to point at, so the block never runs and the `source.rs:636` hardcode survives
to the screen.

### F2 — "ux.6a made denials real [in this counter]." FALSE for this counter.

`EgressDenied` has exactly two emitters, both in `agentd/src/egress.rs`:
- `record_denied` (`:303`) — `#[deprecated]`, the pre-ux.6a path, no production callers.
- `record_denied_policy` (`:358`) — production callers are **only** `egress.rs:609` and
  `egress.rs:643`, both inside `handle_proxy_request` (`:481`), the HTTP egress proxy.

And `egress.rs:637` says in the code: *"today cos ships no `universal` agents and no
`[egress] proxy_addr`, so **this proxy never starts in production**"* — confirmed by
`main.rs:1209`, which starts the proxy only when `cfg.egress.proxy_addr` is set.

**So `egress_denied` is structurally zero in production, in BOTH transports.** Fixing the
`HttpSource` hardcode would not change the denied number by one.

### F3 — the production denial path emits a DIFFERENT event, which nothing counts.

ux.6a's production-reachable denial is native scheduler admission. It emits
`EventKind::AgentAdmissionDenied` at five sites in `scheduler.rs` (`1294`, `1971`, `1999`,
`2082`, `2178`) with reasons `shutdown`, `global_budget_exhausted`,
`agent_budget_exhausted` — then calls `receipt_denial_once`, whose own doc comment
(`egress.rs:367`) says it writes the signed-receipt half *"without the `EgressDenied`
event — so the same fact is not recorded twice."*

`agent_admission_denied` appears **nowhere** in `agentctl/` or `surfaces/`. Verified by grep.

### F4 — the killer, found by the Claude CEO voice and verified: `0 denied` is CORRECT

Under the shipped config the denial paths are not merely unlikely — they are **unreachable**:

| Gate | Shipped value | Consequence |
|---|---|---|
| `[egress] proxy_addr` | **unset** in `agentd/cos.agents.toml` AND `distro/overlay/etc/agentd/cos.agents.toml` | proxy never starts -> `egress_denied` never emitted |
| `budget_reset_interval` | **86400** in both configs | every budget-denial site is behind `if sched.budget_reset_interval == 0` |

Verified by walking each emission site to its nearest enclosing guard:

| Site | Reason | Nearest `==0` guard | Fires in production? |
|---|---|---|---|
| `scheduler.rs:1294` | `shutdown` | none | **yes** (but shutdown is not a policy verdict — ux.6a settled this) |
| `scheduler.rs:1971` | `shutdown` | `1849` | no |
| `scheduler.rs:1999` | `global_budget_exhausted` | `1849` | no |
| `scheduler.rs:2082` | `agent_budget_exhausted` | `2046` | no |
| `scheduler.rs:2178` | budget (either) | `2046` | no |

All three `receipt_denial_once` calls sit inside those same `== 0` branches. Under a
window, budget exhaustion is a **deferral** (ux.8′), and the code at `:2189` states
receipting a deferral is forbidden.

**So in the operator's real deployment the only denial event that ever fires is
`agent_admission_denied{reason:"shutdown"}`.** `0 denied` is not a lie. It is the truth.
There is no wrong answer on screen to fix.

This also kills the obvious reshape: a counter over `agent_admission_denied` (my own
Approach B, below) would ALSO read ~0 forever, and its acceptance test would only go green
against a config production does not ship — the precise false-green class this repo has
caught repeatedly.

### What the operator can actually see today

| Surface | Sees a production budget denial? |
|---|---|
| AgentDetail `N denied` counter | **No** — counts `egress_denied`, structurally 0 |
| Inspector `Errors` filter | **No** — 7 kinds (`inspector.rs:74`), not this one |
| Inspector `CapDenied` filter | **No** — matches only `capability_denied` |
| Inspector `Egress` filter | **Partly** — matches `action_receipt_emitted`, so the receipt line shows, under a filter named "Egress", with the verdict buried in JSON |
| Inspector `All` + search | Yes, if the operator already knows the string to search for |

The counter is not merely transport-skewed. **It is the wrong metric**, and the filter an
operator would actually reach for (`Errors`) misses the event entirely.

### Answering 0A's three questions

1. **Right problem?** The filed problem (transport asymmetry) is not the real one. The real
   one: *the cockpit cannot tell the operator that the runtime refused to run their agent.*
   That is worth fixing; the filed framing is not the way to fix it.
2. **Actual outcome vs proxy problem?** The filing optimises a proxy (make two transports
   agree) over the outcome (operator learns why the pipeline stopped). Classic proxy
   problem — and this repo's CoS pipeline stalling silently is the exact live pain.
3. **Do nothing?** The false `0 denied` persists and now actively misleads, because ux.6a
   made denials real in the *receipt chain* while the cockpit's dedicated denial number
   stayed structurally 0. A wrong governance number is worse than a missing one.
