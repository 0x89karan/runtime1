# p6.6 — Spawn view

**Branch:** p6.6-spawn-view  
**Depends on:** p6.2 (agentctl spawn CLI), p6.3 (TUI framework)

## Goal

Add a `View::Spawn` to `agentctl watch` — a form-based TUI view that lets the operator pick a template, enter a task, toggle capabilities (pre-checked from the template, deny-by-default), preview the generated `agent.toml`, and spawn the agent.

Mode (a) — generate-and-exec — ships here. Mode (b) — inject-into-running-scheduler — is explicitly deferred (requires a writable `/agents/control` surface, its own sub-task).

## Roadmap acceptance criteria (verbatim)

Spawning from the form produces the same `agent.toml` the CLI would and starts the agent; no capability is granted beyond the template without an explicit toggle.

## Implementation plan

### 1. `SpawnViewState` in `app.rs`

New state struct for the Spawn view:

```rust
pub struct SpawnViewState {
    /// Loaded template list (name, source, description, showcases, suggested_caps)
    pub templates:       Vec<SpawnTemplate>,
    /// Index of the selected template in the list.
    pub template_idx:    usize,
    /// Which field is focused: TemplatePicker | TaskField | CapToggle(n) | ActionButtons
    pub focus:           SpawnFocus,
    /// Task text being typed.
    pub task_input:      String,
    /// Per-capability toggle state: (cap, enabled).
    pub cap_toggles:     Vec<(FormattedCap, bool)>,
    /// Generated agent.toml preview text (None = not yet generated).
    pub preview:         Option<String>,
    /// Spawn result message (Ok message or error).
    pub result:          Option<SpawnResult>,
}
```

`SpawnFocus` enum: `TemplatePicker`, `TaskField`, `CapToggles`, `ActionGenerate`, `ActionSpawn`.

`SpawnResult`: `Ok(String)` (path to the agent.toml) | `Err(String)`.

When the user enters the Spawn view, `SpawnViewState` loads the template list via `TemplateResolver::from_env().list()`. On template selection, the capability toggles are rebuilt from the template's `suggested_caps` (all pre-checked). `task_input` is empty by default.

### 2. `handle_spawn_key` in `mod.rs`

Following the same pattern as `handle_memory_key`. Extracted function, unit-tested.

Key bindings:
- `↑`/`k` — select prev template (while focus = TemplatePicker)
- `↓`/`j` — select next template (while focus = TemplatePicker)
- `Tab` — cycle focus: TemplatePicker → TaskField → CapToggles → ActionGenerate → ActionSpawn → TemplatePicker
- `Enter` — in TaskField: advance to CapToggles; in ActionGenerate: generate preview; in ActionSpawn: spawn
- Type chars — append to task_input (while focus = TaskField)
- `Backspace` — delete last char from task_input (while focus = TaskField)
- `Space`/`Enter` — toggle the focused capability
- `↑`/`k` / `↓`/`j` — move between cap toggles (while focus = CapToggles)
- `Esc`/`q` — back to Dashboard (if not in TaskField); if in TaskField, deactivate text input
- `[g]` — shortcut for Generate
- `[r]` — shortcut for spawn (Run)

When `preview` is Some, the bottom half shows the generated `agent.toml`.

`result` shows a status bar: green for success ("agent.toml written, spawning agentd…"), red for error.

### 4. Spawn action

The spawn action in the TUI calls the same logic as the CLI:
1. Resolve template (already loaded in `SpawnViewState`)
2. Build `extra_caps` from enabled toggles
3. Call `to_agent_config(task, extra_caps)`
4. `toml::to_string_pretty(&config)`
5. Write to a temp file
6. Exec agentd (replaces the TUI process — consistent with CLI mode (a) behavior)

Since `exec_agentd` is `pub(crate)` in `spawn.rs`, expose it or duplicate the logic. Actually, looking at the existing code, `exec_agentd` is `fn` (private). We need to make relevant functions `pub` or move them to a shared module.

Alternatively: the TUI spawn action calls `spawn::run(args)` with the template name, task, and selected caps translated to `--cap-add` args. This reuses the existing CLI path completely.

**Decision needed:** inline the spawn logic in the TUI (reuse CLI functions directly), or delegate to `spawn::run(args)` which execs agentd and replaces the process.

Since the CLI path already does exactly what we want (and the `--force` flag can bypass the guard when caps are pre-loaded from the template's own suggested list), the cleanest approach is to reuse `spawn::run()` directly by constructing `spawn::Args` from the form state.

However: `spawn::run()` calls `exec_agentd()` which replaces the process (`exec()` on Unix). This means the TUI process is replaced — the TUI disappears and agentd takes over. This is correct and expected for mode (a).

### 5. Cap representation

The `SpawnViewState` stores caps as `(display_string, enabled, capability)`. The `capability` field (a `Capability` value) is what gets passed to `to_agent_config()`. `display_string` is what the user sees: "FsRead {/workspace}", "KbRead {agent/journaler}", etc.

Caps come from `template.card.suggested_caps` (the same field `cap_add_allowed_by_suggestion` checks against). All pre-enabled by default (the template's suggested baseline).

### 6. Template loading

`TemplateResolver::from_env()` reads the template dirs. Call `resolver.list()` to get `Vec<TemplateEntry>` — each has `name`, `source`, `description`, `showcases`. Then call `resolver.resolve(name)` to get the full `TemplateConfig` with `card.suggested_caps`. Load the full config for the selected template on selection change.

Loading happens:
- On entering the Spawn view (or on first tick if templates not yet loaded)
- On template selection change (to update cap toggles)

### 7. Plain mode

`run_plain()` gets a new Spawn section stub: "Spawn view not available in plain mode. Use: agentctl spawn <template> --task '...'" — since plain mode is for non-TTY and exec'ing agentd from there is the native CLI path.

### 8. New tests

Following the established pattern (unit tests at the bottom of each module):

- `spawn_view_initial_state_has_no_preview` — SpawnViewState::default() has no preview
- `spawn_handle_key_tab_cycles_focus` — Tab cycles through all SpawnFocus variants
- `spawn_handle_key_task_input_accumulates` — char keys append to task_input when TaskField focused
- `spawn_handle_key_backspace_removes_last_char` — Backspace removes last char
- `spawn_handle_key_cap_toggle_flips` — Space/Enter toggles a capability
- `spawn_handle_key_esc_returns_to_dashboard` — Esc from TemplatePicker goes to Dashboard
- `spawn_handle_key_arrow_selects_template` — ↑/↓ changes template_idx
- `render_spawn_no_templates_shows_empty` — renders gracefully with empty template list
- `render_spawn_with_template_shows_caps` — renders cap toggles from template
- `render_spawn_preview_shown_when_present` — preview section visible when preview is Some

## Decisions to be made (D-list for review phases)

### D1: Spawn exec behavior in TUI

When the user hits Spawn, mode (a) means `exec agentd` which replaces the TUI process. The terminal returns to normal (agentd is in the foreground). This is honest about the constraint — mode (b) "inject into running scheduler" requires the `/agents/control` surface and is deferred.

- **A) exec agentd (replaces TUI)** — consistent with CLI, honest, simple. User sees agentd output. Press Ctrl+C to kill agentd.
- **B) spawn agentd as a child** — TUI stays running, agentd runs in background. Requires forwarding agentd's output somewhere (a new log pane?). Out of scope for p6.6.

**Recommendation: A** — consistent with the CLI contract; mode (b) is the roadmap item after this.

### D2: Template loading strategy

- **A) Load on Spawn view enter** — load all templates when the user switches to the Spawn view. Simple, fresh.
- **B) Load on startup** — load all templates at TUI start. Templates are small; startup cost is negligible.

**Recommendation: A** — lazy load matches the pattern already used for Memory and Topology views (only read data while the view is active).

### D3: Capability display format

The `suggested_caps` from a template are `Vec<Capability>`. How to display them:
- **A) Full struct display** — "FsRead {/workspace}", "KbRead {agent/journaler}", "Spawn"
- **B) CLI alias display** — "fs-read:/workspace", "kb-read:agent/journaler", "spawn"

**Recommendation: A** — matches the INTERFACE.md mockup; struct form is what the user sees in agent.toml and FUSE files; consistent with System view's sandbox display.

## GSTACK REVIEW REPORT

### Phase 1: CEO Review

**Verdict: PASS**

Strategic alignment: correct next increment per roadmap; completes the Phase 6 "full operator workflow" (read → spawn → observe). Mode (a) ships first, mode (b) gated on the control surface — correctly scoped.

Scope is tight: no MCP server display, no cap-add-beyond-suggested, no template filter. These are all correctly deferred.

One concern surfaced: exec'ing agentd replaces the TUI process abruptly. The operator should see a confirmation or "spawning..." message before the terminal switches over. **Mitigation in scope:** the Generate → Spawn two-step gives the operator a review checkpoint; the Spawn action will show the agent.toml path in the footer before exec.

CEO score: 9/10. Ready for Phase 2.

### Phase 2: Design Review

**Verdict: PASS** (UI scope detected)

The Spawn view is the first interactive form in the TUI. Key UX patterns:
- Template list at top (arrow keys to navigate, highlighted with `▸`)
- Task field below (text cursor shown as `_` at end; all chars appended, Backspace deletes)
- Capability checkboxes below task (`[x]` checked, `[ ]` unchecked; Space to toggle; arrow keys to move between caps)
- Preview pane at bottom (Generated TOML, scrollable)
- Footer shows active key hints contextually

One design concern: Tab cycling through 5 focus stops is complex. **Simplified:** use section headers as focus anchors; Tab moves between Template | Task | Caps | Buttons only. Within Caps, arrows navigate; within Buttons, arrows/Tab advance. This is standard TUI form UX.

Design score: 8/10. Ready for Phase 3.

### Phase 3: Eng Review

**Verdict: PASS WITH NOTES**

Key engineering concerns and resolutions:

1. **Terminal cleanup before exec**: `run_tui` must call `disable_raw_mode()` + `execute!(LeaveAlternateScreen)` before calling `exec_agentd`. The `CleanupGuard` can be dropped explicitly (via a wrapper), or cleanup called explicitly before exec. The `pending_exec: Option<PendingSpawn>` pattern defers the exec until `run_tui`'s main loop where the guard is in scope.

2. **`exec_agentd` and `resolve_agentd` accessibility**: Currently private in `spawn.rs`. Need `pub(crate)` for reuse from `run_tui`. Alternatively: store the generated TOML path in `PendingSpawn` and call `exec_agentd` from `run_tui` directly.

3. **`format_cap()` in `spawn.rs`**: Currently private. Needs `pub(crate)` for display in `views.rs`.

4. **Template loading avoids crate boundary issues**: `App` stores `spawn_view: SpawnViewState`; `SpawnViewState.load()` calls `crate::build_resolver(None, None).list()` (uses env paths). Loaded once when `view == View::Spawn && !spawn_view.loaded` in `apply_snapshot`.

5. **Cap toggle data**: `Vec<(Capability, bool)>`. The `Capability` type is `pub` in `agentd`. Import it in `agentctl/src/watch/app.rs` (agentctl already imports agentd types in spawn.rs).

6. **Tests**: 20+ new tests targeting key dispatch, rendering, and loading. `make clippy-linux` clean required before ship.

7. **`watch/spawn.rs` new module**: Holds loading helpers. `SpawnViewState` and focus/result enums live in `app.rs` (same pattern as `MemoryPaneState`).

Eng score: 8.5/10. Ready for Phase 3.5.
