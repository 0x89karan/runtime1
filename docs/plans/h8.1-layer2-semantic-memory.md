# h8.1 — Layer 2 Semantic Memory

**Increment:** h8.1  
**Version:** v0.64.0 (tentative)  
**Status:** Planning  
**Branch:** h8.1-layer2-semantic-memory (not started)  
**Track:** HARNESS with minimal Rust changes — Python sidecar + Docker configuration; two small Rust changes required (see Scope)  

## Goal

Attach a hybrid vector+keyword knowledge base as an MCP sidecar reachable via the HTTP/SSE transport
shipped in p7.1. Agents get semantic search alongside the existing BM25 lexical store (Layer 1) with no
change to the tool names they call — `kb_search`, `kb_put`, `kb_get` work identically whether they
hit Layer 1 or Layer 2. Operators opt into Layer 2 by adding one service to docker-compose and
one `[[tools.mcp_servers]]` entry with `url =` pointing at the sidecar.

## Context

Layer 1 (p5.5, `memory/` crate, redb-backed BM25) is embedded in `agentd` — zero infrastructure,
keyword-only. It works well for structured recall ("what did I decide about X?") but misses semantic
matches ("what relates to X even without the word X?"). Layer 2 adds a second KB tier that agents
can register additional tools against. DESIGN-memory.md §4 and §9 Q1 (decided) define the two-layer
architecture.

The broker (`cred.3`, v0.60.0) is live. It can issue short-lived tokens for upstream APIs including
embedding providers, but the sidecar is a Docker service (not a subprocess of agentd) so it is
provisioned independently via Docker secrets / environment.

h8.1 is a HARNESS increment. It adds:
- One Python MCP sidecar (`docker/semantic_kb_mcp.py`) that implements `kb_search`, `kb_put`, `kb_get`
  backed by Qdrant + Voyage AI embeddings
- One new Docker Compose service (`qdrant`) plus the semantic-kb-mcp sidecar
- An optional template update (`templates/librarian.template.toml` + `templates/librarian-semantic.template.toml`)
- Docs in `docs/MCP_SERVERS.md`

No `agentd` Rust changes are needed. The existing `McpHttpClient` (p7.1) connects to the sidecar;
the existing `KbRead`/`KbWrite` capability gates still apply.

## Architecture

```
agentd ──[McpHttpClient / HTTP+SSE]──> semantic-kb-mcp (Python, :8020)
                                              │
                     ┌────────────────────────┤
                     ▼                        ▼
           Qdrant (:6333)             Voyage AI (remote embed API)
        (vector store only)          voyage-3-lite / voyage-3
              (h8.1)                   (or VOYAGE_MOCK_EMBEDDINGS=1)
```

**Engine decision:** Qdrant for h8.1. HelixDB (graph+vector, Rust-native) has no stable public Docker image as of the autoplan date; Qdrant is production-grade, Rust-native, purpose-built, and has an excellent official `qdrant/qdrant` Docker image. HelixDB is the upgrade target for h8.2+ once it has a stable Docker release. The sidecar file is named `semantic_kb_mcp.py` (engine-neutral).

**Tool contract (same names as Layer 1):**

| Tool       | Sidecar behaviour                                      |
|------------|--------------------------------------------------------|
| `kb_put`   | Embed content → upsert vector + store raw text in Qdrant |
| `kb_get`   | Fetch entry by key from Qdrant                          |
| `kb_search`| Embed query → vector ANN search → ranked hit list       |

**Search strategy for h8.1: pure vector.** Qdrant does not have built-in BM25; implementing a
separate BM25 index in Python adds ~50-80 lines and a durability concern (index must survive container
restart). For h8.1, `kb_search` is pure vector ANN (Qdrant's dense vectors). RRF fusion (combining
Qdrant vector with sparse/keyword search) is deferred to h8.2+ once `voyage-3` sparse vector support
or Qdrant sparse vector endpoints are validated. Agents call one `kb_search` and get vector-ranked
results; the agent surface is identical to what RRF would produce.

**Credential model:**

- `VOYAGE_API_KEY` is read from the sidecar container's environment (set in `docker-compose.yml`
  like `BRAVE_SEARCH_API_KEY`)
- `ANTHROPIC_API_KEY` is never passed to the sidecar — it only needs the embedding key
- The cred.3 broker is NOT used here because the sidecar is a peer Docker service, not an
  agentd subprocess; broker pattern applies only to stdio MCP servers spawned by agentd

## Resolved Decisions

### D1: Engine — RESOLVED: Qdrant for h8.1; HelixDB deferred to h8.2+

HelixDB (`ghcr.io/helixdb/enterprise-dev:latest`) has a Docker image, but its query surface is a
**graph traversal DSL** — every operation is a `POST /v1/query` with a JSON AST carrying
`request_type`, `queries[]`, and `returns[]` graph steps. There is no simple vector upsert/search REST
API. Local dev is lifecycle-managed by the `helix` CLI, not a plain `docker-compose` service. This
makes it a poor fit for a HARNESS increment: the Python sidecar would need to construct, sign, and
parse DSL JSON rather than calling simple REST endpoints. The original open-source v1 (LMDB) is
deprecated; the active product (Helix Cloud v2) is a cloud-native LSM graph store.

Qdrant (`qdrant/qdrant`) runs as a plain docker-compose service with a straightforward REST API
(`POST /collections/{name}/points/upsert`, `POST /collections/{name}/points/search`) — exactly
the right fit for a ~350-line Python sidecar. HelixDB is the architectural target for h8.2+ when
the graph-aware KB (provenance links, agent memory graphs) is worth the DSL integration cost.
Sidecar file is named `semantic_kb_mcp.py` (engine-neutral) to keep the swap clean.

### D2: Tool namespace — RESOLVED: same names (kb_put/kb_get/kb_search)

DESIGN-memory.md §4: "An agent cannot tell whether retrieval was lexical-local or hybrid-remote."
Same names preserved. Collision with native Layer-1 tools resolved via Rust change D7 below.

### D3: Transport — RESOLVED: HTTP/SSE MCP (p7.1)

Docker peer service; stdio impossible. Uses `url = "http://semantic-kb-mcp:8020"` with
`allow_insecure_local: true` (see Rust change D6).

### D4: Embedding tier — RESOLVED: configurable, default voyage-3-lite

`VOYAGE_MODEL` env var; default `voyage-3-lite`. `VOYAGE_MOCK_EMBEDDINGS=1` returns deterministic
zero vectors — required for self-tests and no-key local evaluation.

### D5: Search strategy — RESOLVED: pure vector for h8.1; RRF deferred

Qdrant has no built-in BM25; a Python BM25 index adds durability complexity. h8.1 uses pure
vector ANN. RRF (sparse+dense fusion) is deferred to h8.2+.

### D6: http:// URL validator — RESOLVED: `allow_insecure_local: bool` on McpServerConfig

`McpServerConfig.validate()` at `config.rs:612` hard-rejects `http://`. Fix: add
`allow_insecure_local: bool` (default false, `#[serde(default)]`); when true, `http://` is
accepted with a `tracing::warn!` at startup. Two new tests required:
`http_server_allow_insecure_local_ok` + `http_server_insecure_local_rejected_without_flag`.

This is a minimal Rust change confined to `agentd/src/config.rs`.

### D7: Tool name collision — RESOLVED: `tool_override: bool` on McpServerConfig

`registry.register()` returns `Err` on duplicate name. Fix: add `tool_override: bool`
(default false, `#[serde(default)]`) to `McpServerConfig`. When true, MCP tools with names
that match an already-registered native tool silently shadow the native tool (remove native,
insert MCP). Operators must explicitly opt-in; default false means accidental shadowing
emits an error, not silent override. One new test: `mcp_tool_override_shadows_native`.

This is a minimal Rust change confined to `agentd/src/config.rs` + `agentd/src/tools/mod.rs`.

### D8: Python dependencies — RESOLVED: requests-only

Raw HTTP to Voyage AI REST API using `requests`. No `voyageai` SDK. Consistent with all
existing Docker sidecars. No additional `pip install` needed beyond the base Docker image.

### D9: cred.3 broker exception — DOCUMENTED

ROADMAP note "embedding API key rides the cred.3 broker" applies to stdio MCP servers spawned as
agentd subprocesses. The sidecar is a Docker peer service, so `VOYAGE_API_KEY` is provisioned via
Docker environment (same pattern as `BRAVE_SEARCH_API_KEY` in the `cos` service). The broker does
not govern Docker-level peer services. This is a deliberate architectural exception.

## Scope

### New files

1. **`docker/semantic_kb_mcp.py`** — Python MCP server (~350 lines):
   - Plain `mcp` library over streamable HTTP (consistent with other sidecars)
   - `kb_put(segment, key, content, metadata?)` → embed → upsert Qdrant
   - `kb_get(segment, key)` → Qdrant point fetch by ID
   - `kb_search(segment, query, limit?)` → embed query → Qdrant vector ANN → return ranked list
   - `QDRANT_URL` env for storage backend URL (default `http://qdrant:6333`)
   - `VOYAGE_API_KEY` env for embedding API
   - `VOYAGE_MODEL` env (default `voyage-3-lite`)
   - `VOYAGE_MOCK_EMBEDDINGS=1` env for deterministic zero-vector testing (no API key needed)
   - `VOYAGE_DIMENSION` env (auto-detected from model: voyage-3-lite=512, voyage-3=1024)
   - 6+ self-tests runnable with `python3 semantic_kb_mcp.py --test` (no external services)
   - SSRF guard on `QDRANT_URL` (loopback/private ranges allowed, external blocked)

2. **`templates/librarian-semantic.template.toml`** — librarian variant with semantic KB:
   - `gated_requires = "VOYAGE_API_KEY"` warning
   - `[[tools.mcp_servers]]` entry: `url = "http://semantic-kb-mcp:8020"`, `allow_insecure_local = true`, `tool_override = true`

## Security

- **SSRF:** sidecar does not proxy arbitrary URLs; storage backend URL is validated at startup
- **Key isolation:** `VOYAGE_API_KEY` lives only in the sidecar container; never passed to agentd; never logged
- **Tool output cap:** `kb_search` results capped at 100 hits × 8 KB each (per existing Layer-1 convention)
- **Content-type enforcement:** sidecar returns `application/json` always (no content-type sniffing)
- **Input validation:** key must pass `validate_child_id` equivalent (no path separators, ≤128 chars)
