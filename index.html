How the pieces are named

Three names, one stack — worth getting straight before anything else.

the project

runtime1

The whole open-source project: the operating system, the operator tooling (agentctl), the tool servers, the verification pipeline, and the docs. When you clone the repo or read this site, you are looking at runtime1.

the operating system

agentOS

The agent operating system inside runtime1 — the part that actually runs the agents. A minimal Linux base whose entire userspace is the agent runtime: no desktop, no apps, no login shell, just agents and the tools they invoke.

the runtime process

agentd

agentOS's runtime binary — a ~2 MB Rust daemon that boots as PID 1 and is the userspace. It holds the scheduler, the capability system, the memory substrate, the gateways, and the flight recorder.

The idea in three sentences

01 · agents, not apps

A new primitive

A normal OS schedules processes and CPU time. agentOS schedules agents and the resources that actually matter for them: inference slots, token budgets, dollars, and tool access. The runtime (agentd) boots as PID 1 — there is no desktop, no apps, just agents and their tools.

02 · governance built in

Bounded by construction

Agents are useful precisely when you stop watching them — and that's when they're dangerous. So the boundary does the supervising: capability grants, a budget fuse that actually stops a runaway loop, approval gates for risky actions, and a flight recorder that logs every step.

03 · evidence, not promises

Verify, don't trust

Model calls are receipted into a hash-chained, Ed25519-signed log you can verify offline. The roadmap extends this to every action class, custody-anchored audit packets, and zero-knowledge proofs that the published decision log is consistent with the policy — without revealing the policy.
