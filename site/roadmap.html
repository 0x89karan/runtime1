state of the experiment

What's built, what's being worked on, what was rejected.

Organized by track, not by release. No dates and no delivery promises — this is one developer's experiment, and the ordering below reflects intent, not a schedule.

Tracks

The runtime

built & dogfooded

agentd as PID 1: the agent state machine, a cooperative multi-agent scheduler, metered admission (tokens, dollars, wall-clock) with a rolling reset window, checkpoint/restore that survives a SIGTERM mid-tool-call, and the flight recorder that every other track reads from.

Open question: can the scarce resource of an operating system really be inference and spend rather than CPU time, all the way down?

Memory

built & dogfooded

Four tiers with provenance: in-context working set, per-agent short and long-term stores on an embedded key-value engine, a shared knowledge base with namespaces and mutability classes, and a semantic index for retrieval. Exposed to agents as tools and to the operator through the filesystem surface.

Open question: how much context management should runtime1 do for an agent before it starts making the agent worse at its job?

Capabilities & isolation

built

Every agent runs with an explicit grant set. Landlock, seccomp and namespaces enforce it at the process boundary; gVisor provides a stronger tier for untrusted workloads; spawned children can only receive an attenuated subset of the parent's grants, and an over-grant is rejected rather than silently clamped. A linter catches the misconfigurations that would otherwise fail open.

Open question: is a capability layer ever enough for agent-generated code, or does unsupervised autonomy always need a hardware boundary underneath?

Tools & connectors

built & dogfooded

MCP is the tool ABI, over stdio and streamable HTTP. A credential broker holds OAuth tokens and API secrets so agents never do — they get inert placeholders, and the real values are injected at the egress boundary. Event triggers (cron, filesystem, webhook) let the world wake an agent up.

Open question: does brokering every credential actually shrink the blast radius in practice, or just relocate it?

Operator surface

built

agentctl: a terminal cockpit for watching agents, topology, memory, logs and spend, with row-level control verbs (cancel, set budget, park) and an approval queue. A management HTTP API behind the same auth, plus reach outside the terminal so a standing agent can ask a question and get an answer back.

Open question: what is the smallest surface that lets someone leave agents running and still trust what happened while they were away?

Evidence & verification

built mostly specced

Built: a hash-chained, Ed25519-signed receipt log of model calls (allowed and denied), rotated into independently verifiable segments, with an offline verifier.

Specced, not built: full action coverage and custody anchoring (gov.1), an auditor-side trust root (gov.2), a single pure policy-evaluation crate shared by enforcement and proving (zk.0), a decision journal with a native replay verifier (zk.1), zero-knowledge batch replay proofs (zk.2) and verification across many machines (zk.3). The full ladder and its limits are on the verification page.

Open question: can a stranger check what an agent did without trusting the machine that did it — and how much of that is honestly achievable at all?

The workload

running in progress

The reference implementation, not the product: a standing chief-of-staff built from three of the shipped agent templates — read a real inbox, dedupe against semantic memory, publish a morning brief. It exists to prove the substrate under real conditions, and it is the source of most of the bugs worth fixing. Currently being made reliable — the scheduler needs native cron so no model call sits on a clock boundary (attn.4).

Open question: does a bounded agent team actually save its operator time, or just move the work somewhere else? Fourteen days of use decides it.

Hardware isolation

specced

A per-agent microVM boundary rather than a shared kernel: hypervisor spike, a vsock control plane, a Python-free guest, and microVM as a tier in the existing isolation ladder. Beyond it sits an attested governor — policy evaluation, the evidence writer, and the credential broker inside a measured confidential guest, with the signing key sealed to the measurement. That is the only approach reviewed so far that closes, rather than narrows, the "was every action recorded" gap — and only for brokered actions.

Open question: is hardware attestation worth its complexity for a single-operator system, or is it only meaningful at scale?

Skills

specced

Procedural knowledge as a governed runtime1 object: an agent that learns a repeatable procedure should be able to keep it, share it, and have it reviewed — under the same capability rules as everything else, with synthesized skills quarantined until approved.

Open question: is a skill just a prompt with better packaging, or a genuine runtime1 primitive that deserves its own lifecycle?

Considered and rejected

The reasoning behind a "no" is usually more useful than another line on a wish list, so the notable ones are kept here rather than quietly dropped. Each was written down at the time; none are hypothetical.

Zero-knowledge proofs in the authorization path

not doing

The original design proved each policy decision in a zkVM before the action ran. At seconds per proof against thousands of calls a day, that is a denial-of-service against the runtime it protects. Worse, it would have claimed "mathematical certainty that policy was enforced" while the host still chose which actions to submit for proving. Reshaped into post-hoc batch replay proofs with an honest claim; the original is dead.

A per-action signed receipt for every tool call

not doing

Widening the existing receipt chain to every action sounded obvious until the cost was measured: a synchronous disk sync per receipt on the caller's thread, inside a writer that fails closed, on a file the runtime reads at boot. Replaced by signing a batched projection of the flight log — which also gets full coverage, without putting a fsync in front of every tool call.

A per-agent request rate cap

not doing

Built, then withdrawn before it shipped. The counter was monotonic over the process lifetime rather than a real rate limit, so a long-running agent would have hit a hard failure after days of normal operation — with the restart policy faithfully keeping the process alive to reach it. The mechanism and three possible fixes are written down; the feature is not shipping until one of them is real.

Local model weights

not doing

Cognition is remote by design. Shipping weights is the difference between an operating system that is genuinely a couple of megabytes and one where "light" means a lean shell around something heavy. A local backend can arrive later as another gateway implementation — never as a core assumption.

Multi-tenancy

not doing

One person's agents on one machine, mutually trusting, in-process. Capability scoping between agents exists for least privilege, not because agents distrust each other. Adding tenancy boundaries would change nearly every subsystem and buy nothing for the case being tested.

How this page stays honest

Labels here follow the same rule as the rest of the site: a claim of "built" means code enforces it and tests cover it, not that a config file mentions it. When something moves from specced to built, the claim moves with it — and when something is discovered to be less true than claimed, it moves back. That has already happened more than once, and those corrections are in the repo's history rather than edited out of it.
